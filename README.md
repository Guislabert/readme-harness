> A standardised, modular framework for authoring project **README / Landing** pages — pick modules, apply a skeleton, ship a consistent page for every new repository. Inspired by [DeepSeek-Harness] and maintained by **@Guislabert**.

## Why

Every new repository starts by re-writing the same README from scratch: no
consistent structure, no shared vocabulary, the same choices re-made each time.
Across a portfolio of repos the pages drift apart — different badge rows,
different link conventions, different bump discipline.

> **Readme Harness is the standardised base layer** on top of which each new
> project's landing page is assembled. You define the structure once, then
> re-use it everywhere.

## What

A plug-in framework, not a single template. It ships:

- a **skeleton** — a copy-able, commented README/Landing page with every
  section's place-holder marked.
- **modules** — re-usable, independently landable components (a badge row,
  capability pills, hero image, before/after proof…).
- a **registry** — the single source of truth for which modules exist.
- a **generator** — one command that assembles a new project's README from
  skeleton + chosen modules.

## Structure

```
readme-harness/
├── README.md                 #  en-GB main page (this file)
├── README.zh-CN.md           #  Simplified-Chinese separate page
├── SPEC.md                   #  framework spec: module/registry/version discipline
├── REGISTRY.md               #  module registry (single source of truth)
├── module/                   #  plug-in modules (one landable dir each)
│   └── badges-google/        #    Google four-colour badge module
├── skeleton/                 #  copy-able commented skeleton
│   └── README.template.en.md
├── tools/
│   └── generate.mjs          #  one-command README scaffold generator
└── LICENSE
```

## Modules

| Module | Purpose | Land as |
|---|---|---|
| `badges-google` | Google four-colour badge row (CI·Version·npm·License) | `module/badges-google/` |

> The four colours are one instance of a broader **semantic colour palette** —
> see `module/badges-google/README.md` for extending beyond 4 badges.

## Quick start

Apply the harness to a new repository in three steps:

```sh
# 1. copy the skeleton
cp -r skeleton/ my-new-repo/

# 2. pick modules from the registry
cp -r module/badges-google my-new-repo/module/

# 3. generate the README from skeleton + modules
node tools/generate.mjs my-new-repo
```

The generator **auto-detects** the language/dependency manifest (`package.json`,
`Cargo.toml`, `go.mod`, `pyproject.toml`), the version, any CI workflow, and
which modules are present. If your repo already has a `git remote origin` it
extracts the **owner/repo** so the CI badge and license line point at the real
GitHub pages (no placeholders). No origin yet? Set
`README_HARNESS_OWNER=<your-username>` (or point origin) and re-run.

## Adopting

`Readme Harness` follows SemVer and the version-guard discipline enforced by
`tools/version-check.mjs`: `package.json.version === CHANGELOG newest section
=== README badges`. Version bumps are release points, not push points. See
[SPEC.md](SPEC.md).
